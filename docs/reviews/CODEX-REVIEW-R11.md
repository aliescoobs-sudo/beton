Reviewed on **2026-11-05**. Baseline: `2cfc0bd05c394f86ac812d977b63577ed66f1b93`. Reviewed head: **`52c285895a3897685c5e8f21b0736e2d11403acd`**, fetched as `origin/main` in `/Users/macplanet/BELGOBETON-finance`. However, the training configuration enables the still-unfixed public PIN endpoint, and credential-file handling and the training-database admission checks need correction. ## Findings ranked by severity

No blocker-class unauthenticated remote compromise was established by this static review. The **high** findings nevertheless prevent approval of the unchanged Funnel deployment. “Fictitious data” does not make passwords, session tokens, encryption keys, registry credentials, or the host's Tailscale identity fictitious.

### R11-01 — High — training enables the unresolved PIN-attempt race on a public endpoint

**Verified:** `init-env.sh` enables `FIELD_APP_ENABLED=true`. The PIN login still reads `locked_until`, checks the PIN, increments failures, and issues/binds a session in separate operations. `field_login_ok()` does not re-check the lock and clears the failure state. The endpoint has no equivalent of the office login's per-IP guard. Generating six-digit training PINs is an improvement in entropy, not an atomic attempt limit. The checkpoint explicitly defers the original **F11**.

**Inference:** concurrent requests admitted before the first lock can continue verifying guesses; a successful request already in flight can clear a newly established lock. This weakens the advertised five-attempt limit and permits avoidable authentication/Argon2 load. It does not prove a PIN can be recovered within a particular time, and an already-bound foreign device is still refused. The first binding and post-release windows remain relevant.

Evidence: [`scripts/training/init-env.sh:32`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/scripts/training/init-env.sh#L32), [`field/service/auth.ts:173`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/field/service/auth.ts#L173), [`auth.ts:197`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/field/service/auth.ts#L197), [`auth.ts:224`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/field/service/auth.ts#L224), [`0085_field_login.sql:24`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/db/migrations/0085_field_login.sql#L24), [`CP-PROD-PLAN.md:211`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/docs/checkpoints/CP-PROD-PLAN.md#L211).

**Required for Funnel:** fix atomic attempt reservation, lock re-check before issuance, minimum PIN length, and abuse limiting; or keep `FIELD_APP_ENABLED=false` and exclude driver/pump-phone training from the public instance. An Origin check does not limit a non-browser client's guesses. Funnel makes the endpoint accessible to the internet, not merely to authenticated tailnet members. [Tailscale Funnel](https://tailscale.com/docs/features/tailscale-funnel).

### R11-02 — High — training admission is one-way; an unmarked populated database is accepted

**Verified:** startup refuses a marked training database with training mode off, and the environment refuses training alongside `REAL_DATA=true` or `APP_ENV=production`. But `trainingBootProblem({trainingMode:true, databaseSeeded:false, appEnv:'training'})` returns no problem. Startup does not check that an unmarked database is empty. The seed checks only whether the marker exists before starting to add data; it does not first refuse an existing unmarked business dataset. It writes the marker only after the seed's business operations.

**Conditional consequence:** if training credentials target a pre-existing, migrated, unmarked database while the deployment flags describe training, the app can serve its existing contents under the red “fictitious data” banner. Starting the app directly does not require a successful seed. A seed attempt can also modify an unmarked database before later failing, for example on an existing owner. The dedicated Compose project and fresh-volume procedure reduce this risk in the intended installation; this is not a remote way to change connection strings or flags. The guard itself does not establish the promised database separation.

Evidence: [`src/lib/training.ts:15`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/lib/training.ts#L15), [`boot.ts:52`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/platform-security/boot.ts#L52), [`seed-training.ts:93`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/scripts/seed-training.ts#L93), [`seed-training.ts:112`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/scripts/seed-training.ts#L112), [`seed-training.ts:466`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/scripts/seed-training.ts#L466).

**Required:** reserve a fresh database for initialization, refuse nonempty unmarked databases before any seed write, and require a completed training identity/marker before serving training traffic. Keep bootstrap separate from serving. Do not infer that data are fictitious from environment flags or a banner alone. Refusing the CLI importer does not prevent manual entry or a database restore.

### R11-03 — High — changing the public URL can briefly expose all app secrets locally

**Verified:** `set-url.sh` copies the app environment into a predictable temporary filename using shell redirection and restricts permissions only afterward. It does not set `umask 077` or create the temporary file exclusively. The production `deploy.sh` has the same create-then-chmod pattern in `set_image()`.

**Conditional consequence:** with an ordinary `022` umask and a checkout traversable by another local user, the new file is readable while it contains database credentials, the session-signing secret, and encryption keys. An existing permissively readable temporary file is also reused. A later chmod does not undo a read already performed. The iMac's actual umask and parent-directory access were not inspected; this is a local exposure, not a claim that the file is publicly downloadable over HTTP.

Evidence: [`scripts/training/set-url.sh:10`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/scripts/training/set-url.sh#L10), [`scripts/ops/deploy.sh:23`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/scripts/ops/deploy.sh#L23). The training instructions require this URL-setting operation immediately around public exposure: [`CP-TRAINING-IMAC-FR.md:55`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/docs/checkpoints/CP-TRAINING-IMAC-FR.md#L55).

**Required:** create a private temporary file from the outset in a protected directory, refuse symlink/pre-existing-file substitution, and rename atomically. Apply the same treatment to deployment secrets. This assessment inspected the scripts only, not environment-file contents.

### R11-04 — High — the accounts directory is world-writable and the secret writer trusts existing files

**Verified:** startup creates `out/` with mode **1777**. The seed uses `writeFileSync(path, secrets, {mode:0o600})` without exclusive creation or a no-follow policy, then chmods the path. The mode argument protects a newly created file; it does not first make an existing file private. The marker is inserted before this write, so a failed credential-file write can also leave a seeded database whose next seed invocation returns “already seeded.”

**Conditional consequence:** a local user able to traverse the checkout and write into `out/` can pre-create the accounts destination as their own writable/readable file or substitute a link. The default write follows/reuses that path. On a filesystem honoring the declared Unix modes, secrets can be observed before the subsequent chmod, or remain readable if chmod fails on an attacker-owned file. The sticky bit restricts deletion of other people's files; it does not prevent pre-creation. I did not inspect the real directory, accounts file, or Colima's actual ownership mapping.

Evidence: [`training-up.sh:13`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/scripts/training-up.sh#L13), [`seed-training.ts:466`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/scripts/seed-training.ts#L466), [`docker-compose.training.yml:88`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/docker-compose.training.yml#L88).

**Required:** a private, deliberately owned output directory and exclusive private temporary-file creation followed by a safe rename. Validate custom `TRAINING_ACCOUNTS_FILE` destinations rather than assuming every custom filename is covered by the ignore rules. Handle credential-output failure explicitly before declaring initialization complete. Do not publish the instance if the issued owner/admin credentials may have been exposed.

### R11-05 — Medium — F01 still fails open for NULL plant values

**Verified:** `_pump_in_scope(NULL)` returns `NULL` for a scoped manager: `false OR NULL`. Several callers use `IF NOT _pump_in_scope(...) THEN RAISE ...`. PL/pgSQL does not enter that branch for a null condition. This affects the pump-job insert guard and `set_order_pumped`, and the emergency/redirect checks. In addition, `redirect_candidates` still admits candidate orders whose plant is null, even for a manager's own non-null plant case.

**Conditional consequence:** legacy/unassigned rows are not reliably refused by all mutation doors. A manager requesting candidates for a null-plant case can get candidates across plants; an own-plant case can still reveal unassigned orders and their site labels. Knowing a qualifying case/order ID is a prerequisite. The revised board's ordinary reads do filter by the manager's non-null plant, so the original broad all-plants board leak is fixed. The new seed normally assigns plants to its orders; the residual matters especially when reviewing old datasets or future fixtures.

Evidence: [`0108_pump_scope.sql:8`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/db/migrations/0108_pump_scope.sql#L8), [`0108:27`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/db/migrations/0108_pump_scope.sql#L27), [`0108:79`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/db/migrations/0108_pump_scope.sql#L79), [`0108:225`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/db/migrations/0108_pump_scope.sql#L225), [`0108:245`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/db/migrations/0108_pump_scope.sql#L245). Conditional semantics: [PostgreSQL PL/pgSQL conditionals](https://www.postgresql.org/docs/current/plpgsql-control-structures.html#PLPGSQL-CONDITIONALS).

**Required:** return a definite boolean, treat anything other than true as denial, and filter the candidate rows themselves by the caller's scope. Include null-plant rows in verification of both read and mutation doors.

### R11-06 — Medium — F02's 18-hour offline authorization limit is not actually a hard limit

**Verified:** stored days now carry an owner and timestamp, the service worker no longer caches the API day, and explicit logout clears local state. But `applyLocal()` stamps `savedAt` with `Date.now()` for every local tap. That timestamp is meant to represent the last server response. The interval only syncs pending work/photos; it does not independently expire a day already displayed. With no pending work, it also need not fetch a fresh session and discover revocation.

**Inference:** an offline/local tap extends the apparent server-read lifetime; a page left open can continue showing its day past 18 hours without rechecking expiry. This is more than the documented limitation that a disconnected phone cannot receive immediate revocation. The limit is currently checked on loading a cached day, not continuously enforced. An unlocked phone still has no local PIN lock, as the checkpoint openly acknowledges.

Evidence: [`field-app.tsx:140`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/field/ui/field-app.tsx#L140), [`field-app.tsx:239`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/field/ui/field-app.tsx#L239), [`field-app.tsx:256`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/field/ui/field-app.tsx#L256), [`domain/offline.ts:23`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/field/domain/offline.ts#L23).

**Required before declaring F02 closed:** preserve the last successful server-validation time across local edits, enforce expiry while the page is open and on resume, and check session revocation independently of whether there is queued work. Account labels in localStorage are not an independent local authentication mechanism.

### R11-07 — Medium — training's “push off” guard misses the phone subscription route

**Verified:** `startPushLoop()` and `/api/push` reject training use, but `/api/field/push` checks only the field session and notifications flag. If VAPID keys are present, its GET returns the public key and the phone UI calls `pushManager.subscribe()`, then POST can store the subscription. Training validation does not reject VAPID configuration. The initializer does not generate those keys, so this does not occur in the default generated configuration.

**Conditional consequence:** enabling push keys on a training installation allows browser-to-push-provider subscription traffic despite the “nothing goes out” promise. The server wake-up loop remains disabled; this finding does not claim customer payloads or wake-up messages are sent by that loop.

Evidence: [`api/field/push/route.ts:7`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/app/api/field/push/route.ts#L7), [`push-setup.tsx:40`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/platform-security/ui/push-setup.tsx#L40), [`src/lib/env.ts:122`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/lib/env.ts#L122), [`push-loop.ts:11`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/app/push-loop.ts#L11).

### R11-08 — Medium — the advertised password-only finance training path does not work

**Verified:** training authentication deliberately leaves `user.twoFactorEnabled=false`, while supplying a synthetic fresh factor time to the central guard. Finance's HTTP gate and `financeRequest()` separately require the real `twoFactorEnabled` flag. The seed does not enable the database's finance switch; that switch defaults to false. Setting `FINANCE_ENABLED=true` in the generated configuration therefore does not deliver the promised enabled finance module to the seeded password-only owner/admin/accountant accounts.

**Inference:** finance configuration is refused, and finance reads/exports remain inaccessible or fail through their separate gate. This fails closed; it is not a money leak. It is an integration mismatch that should not be “fixed” by globally widening finance roles or bypassing authentication in production.

Evidence: [`session-gate.ts:68`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/platform-security/auth/session-gate.ts#L68), [`finance/service/http.ts:27`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/finance/service/http.ts#L27), [`finance/service/request.ts:24`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/src/modules/finance/service/request.ts#L24), [`0200_finance_core.sql:33`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/db/migrations/0200_finance_core.sql#L33), [`CP-TRAINING.md:25`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/docs/checkpoints/CP-TRAINING.md#L25).

### R11-09 — Medium — dump-only restore/VPS transfer does not restore attachments or their decryption context

**Verified:** `training-backup.sh` creates a database dump only. Upload bytes are in the separate `filestore` volume and are encrypted with instance-specific keys. `init-env.sh` creates fresh random keys on a new host. The December procedure says to transfer the previous night's dump if training work should follow; it does not transfer the filestore or preserve the necessary encryption-key versions. The same-host restore procedure does not establish recovery after loss of that volume or secret files.

**Inference:** a clean VPS restored as documented can have attachment rows with no blobs and personal fields it cannot decrypt. “Training data” also includes real session bearer tokens and password/PIN hashes in the dump; the 0700 directory, 0600 final file, and outside-repository default are useful controls, but do not make an unencrypted dump suitable for general sharing.

### R11-10 — Medium — the iMac guide treats business-data fiction as protection for real host credentials

**Verified:** the main training checkpoint suggests disabling FileVault or enabling automatic login to obtain unattended restart. It also has the operator authenticate GitHub and Tailscale and save a GHCR pull token using Docker CLI under Colima. The guides explain the password prompt but do not establish a credential helper/keychain configuration or explain Docker's persistent token storage. Without a helper, Docker can persist registry credentials in base64 in its configuration; prompt input alone does not prevent this. [Docker login credential stores](https://docs.docker.com/reference/cli/docker/login/).

**Conditional consequence:** theft or access to an automatically logged-in/unprotected machine can expose app secrets, training owner credentials, the private-image token, and tailnet access state. No actual host setting or credential store was inspected. The installed CLI may already have a helper; the instructions do not require one.

Evidence: [`CP-TRAINING.md:37`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/docs/checkpoints/CP-TRAINING.md#L37), [`CP-TRAINING.md:51`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/docs/checkpoints/CP-TRAINING.md#L51), [`CP-TRAINING-IMAC-FR.md:26`](https://github.com/aliescoobs-sudo/beton/blob/52c285895a3897685c5e8f21b0736e2d11403acd/docs/checkpoints/CP-TRAINING-IMAC-FR.md#L26).

**Required documentation change:** protect the machine and its operator account as a credential-bearing host; keep disk encryption and accept manual unlock unless there is an explicitly accepted alternative. Require a working registry credential helper/keychain and keep the pull token read-only. Hand out each trainee's own line; do not retain terminal transcripts or circulate the all-accounts output. No claim is made that a token is currently leaked.
