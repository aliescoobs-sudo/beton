## Newly identified findings

These are newly identified bypasses/residuals in the scoped implementation, not a claim that every underlying line was introduced after R14. **No blocker found. One high, four medium and two low findings follow.**

### R15A-01 — HIGH: an unresolved old logout prevents signing out after re-login

**Verified in source.** `src/modules/field/ui/field-session.ts:153` silently returns while `signingOut` is true. The flag stays true across the unbounded `await ports.logoutRequest()` at `:181` and is released only in `finally` (`:182`–`:184`). The login screen is made available earlier by `day.signedOut()` (`:179`; `day-controller.ts:176`–`:181`). `field-session.ts:188`–`:191` admits a new sign-in without waiting for that request or separating the old sign-out state. The real logout port is a fetch with no timeout (`field-app.tsx:248`); the login form and successful login path have no pending-logout gate (`field-app.tsx:390`–`:405`, `:418`–`:425`).

**Concrete scenario — inference.** A signs out. The drain completes or reaches its deadline, the login screen appears, but the logout HTTP request hangs before returning headers. B logs in successfully through another request. B later presses sign-out: it returns at line 153, without fencing, clearing the screen, starting a deadline or sending B's logout. B's day remains visible for as long as A's old request remains pending. Thus the first drain's eight-second limit does not protect subsequent logout attempts in the same page.

There is a related response-ordering race: `src/app/api/field/logout/route.ts:7`–`:9` unconditionally deletes the shared field cookie, whereas `src/app/api/field/login/route.ts:25`–`:33` sets it. An old logout response arriving after a successful new login can clear the new cookie. This cookie effect is also an inference; generation checks in JavaScript cannot undo a browser-applied response header.

**Required correction.** Serialize login with completion/failure handling of the prior logout transport and make logout state belong to its originating generation. Every current-session logout must still clear/fence locally even if an older transport never settles. Resolve response/cookie ordering rather than merely adding a UI generation check after fetch. Exercise both a permanently pending request and a late cookie-clearing response before accepting handover.

### R15A-02 — MEDIUM: a timed-out drain can start a fresh photo flush in a later session

**Verified in source.** The outer drain starts `sync('drain')`, then calls `flushPhotos('drain')` only after that await (`src/modules/field/ui/field-session.ts:161`–`:164`). The sync guard is acquired before waiting (`:88`–`:92`), but the photo guard is acquired only when `flushPhotos` is subsequently entered (`:136`–`:139`). `day-controller.ts:66`–`:72` permits drain guards even while fenced. The race timeout does not cancel its promise chain (`field-session.ts:166`–`:172`); successful sign-out invalidates existing guards, not drain guards that have not yet been created. On declining a timed-out sign-out (`:175`–`:177`), the still-running drain is not explicitly expired either.

**Concrete scenario — inference.** A background sync remains pending despite abort. Sign-out's drain waits for it and times out; A confirms leaving. B signs in and queues a B photo. The old sync finally settles: the old sync guard correctly refuses its answer, but the outer drain continues into `flushPhotos('drain')`, now acquiring **B's current generation**. `runFlush` reads the current owner (`:102`–`:104`) and may upload/drop B's photos and initiate a current read (`:105`–`:117`) as work belonging to A's expired sign-out. This does not establish that an A photo is accepted as B or that server authorization is bypassed; it establishes that an expired operation can acquire authority over a new session.

**Required correction.** Capture one sign-out operation/generation guard before the first await, pass it through every stage, and make expiration terminal for that operation, including when the user cancels leaving. Do not mint a fresh drain guard after an earlier stage resumes. The eight-second race must stop continuations, not only stop awaiting them.

### R15A-03 — MEDIUM: owner predicates do not isolate delayed wipes from newer photo writes

**Verified in source.** Account-switch cleanup passes `{ except: data.userId }` before awaiting (`src/modules/field/ui/day-controller.ts:130`–`:134`). Logout passes `{ only: leaving }`, or `'everything'` for unknown ownership (`:176`–`:181`). `src/modules/field/ui/offline-store.ts:41`–`:45` removes the local day/queue synchronously, then **awaits Cache Storage before starting photo deletion**. `photo-queue.ts:39`–`:54` opens IndexedDB and deletes whatever rows satisfy the owner predicate when the cursor eventually runs. There is no captured set of old photo keys, generation or creation cutoff. The later read-epoch check protects UI/queue commits, not the already executing deletion.

**Concrete scenarios — inference.**

1. A read for B encounters A's data and starts a wipe excluding B. Cache Storage stalls. The user signs out and signs in as C; C's current read completes and C queues a photo. The older wipe resumes and deletes C's photo because C is not B. This is precisely a stale wipe reaching another account's new data.
2. A signs out and the A-only wipe stalls. A signs in again and queues a new photo. The previous logout's wipe resumes and deletes the new A photo. An unknown-owner whole-store wipe has the same problem for every later account.

The old wipe no longer clears a newer UI queue after its await, and synchronous localStorage removals do not have this delayed-write problem. Those improvements do not protect the later IndexedDB cursor. The scoped cursor's single transaction guarantees neither which generation it deletes nor protection across the preceding cache/open waits.

**Required correction.** Give photo work a session/cleanup generation or capture the old rows to delete; a stale cleanup must not expand its deletion set to later writes. Avoid a delayed negative owner predicate as the authority to delete future accounts' data. Include three-account handover, same-account re-login and unknown-owner cleanup in storage-level acceptance.

### R15A-04 — MEDIUM: photo capture/enqueue can commit after sign-out and acquire a different owner

**Verified in source.** `src/modules/field/ui/field-app.tsx:257`–`:272` awaits `shrinkPhoto(file)` without opening a work guard. It reads `ownerRef.current` only **after** that await (`:260`–`:267`), queues to IndexedDB without a session check, and calls a fresh `flushPhotos()` afterwards. `photo-queue.ts:27`–`:36` can wait for database opening before `put`; the guard in the later flush does not guard the earlier enqueue. No fence is checked at either storage commit.

**Concrete scenario — inference.** A selects a BL image and encoding stalls. A signs out; B signs in. Encoding resumes, reads owner B and queues the **A image/A trip** under B's owner ID, then attempts to flush it with B's new guard. If the network is unavailable, the image remains queued under B. A same-account variant also crosses the boundary: let A's logout cleanup finish, sign A in again, then release the old encoding; it queues and can upload the pre-logout image after the completed wipe. The server's independent trip checks may reject a foreign trip; this finding does not assert a successful foreign-trip server write. The local image retention and wrong owner assignment occur before that check.

**Required correction.** Capture the owner and generation when capture starts, reject stale preparation before enqueue, and make the asynchronous storage write/cleanup ordering generation-aware. A check only after the put would detect an already committed stale write. Keep the originating guard through any ensuing flush.

### R15A-05 — MEDIUM: stale seed-lock takeover is racy and does not fence a surviving holder

**Verified in source.** `scripts/training-lib.ts:311`–`:322` stats an existing pathname, decides that its mtime is stale, unlinks that pathname and tries exclusive creation. The stat and unlink are not one atomic ownership operation. `:332`–`:337` treats missing heartbeats passively; loss of ownership does not stop the caller. `lock.held()` is checked at sweep entry (`:362`) but never revalidated by the seed before later business/file/marker commits (`scripts/seed-training.ts:217`–`:222`, `:595`–`:621`). The sweep uses file age, not evidence that its creator has died (`training-lib.ts:371`–`:377`). Token-aware heartbeat/release checks improve the ordinary case but do not make check-then-touch/check-then-unlink atomic.

**Concrete scenarios — inference.**

1. Seed A has staged credentials and is suspended before rename for over ten minutes. Its heartbeat also expires. B takes over, sweeps A's still-live stage **before** database refusal, then refuses the nonempty/unmarked business database. A resumes, cannot rename its deleted stage, and leaves a populated unmarked database without completed credential handover. Suspension is a precondition; a recent stage under a regularly beating holder is now protected.
2. B and C both stat the same abandoned lock. B removes it, creates a new lock and passes its held check. C then executes its already-decided unlink, deleting **B's new live lock**, and creates its own. B can continue seeding without owning the lock. Similarly, a holder can refresh its heartbeat between a taker's stat and unlink. Exclusive creation alone does not serialize replacement of an earlier lock.

The atomic database birth claim still prevents two ordinary seeds from both claiming the same unused token. It does not protect the filesystem sweep, which precedes the claim, nor prove a paused file writer dead. No secret disclosure is asserted here; the demonstrated source gap concerns exclusion, deletion and recovery.

**Required correction.** Use exclusion that cannot be stolen from a living writer, or a takeover protocol with atomic ownership and effective fencing of displaced writers at commit. A heartbeat timeout alone cannot prove death. Delete only stages tied to attempts proven unable to resume. Retain the age gate as additional protection, not proof of abandonment.

### R15A-06 — LOW: local startup can re-expose the app through a leftover background Funnel

**Verified in source.** Normal startup does not execute `tailscale funnel --bg`; the explicit call is `scripts/training/go-public.sh:69`. However, `scripts/training-up.sh:21` starts the app before checking Funnel at `:31`. The check accepts an already active single proxy to that app (`scripts/training/funnel-check.sh:21`–`:26`) and does not reset it. The stock app socket is loopback (`docker-compose.training.yml:50`–`:52`); the public Caddy service is behind the explicit `public` profile (`:60`–`:70`). `scripts/training-down.sh:3`, `:9` leaves Funnel closure as an operator action.

**Concrete scenario — inference.** A Mac retains a background Funnel from an old exercise. The app is stopped and later started for a local-only session. When the loopback app returns, the old Funnel can serve it immediately, before inspection; the matching configuration then passes the check. No new explicit publication command is required during this restart. If Tailscale and all other publishers are absent/disabled on the actual Mac, this precondition is absent. No installed-service state was inspected.

**Required correction/containment.** For the stated local-only workflow, retire the public helpers/instructions or require proven closure before starting the app and refuse any active publisher. Do not treat a passing legacy Funnel check as local-only evidence. The exact snapshot's guides still contain Tailscale publication instructions (`docs/checkpoints/CP-TRAINING.md:83`–`:96`); they do not yet describe the user's dropped-Tailscale operating policy.

### R15A-07 — LOW: legacy spent birth rows are accepted as belonging to every reset database

**Verified in source.** `scripts/training-birth.ts:37`–`:43` deliberately reads old tables without `database_name`, yielding a NULL name. `hasBirthRow` accepts a NULL name without checking `consumed` (`:58`–`:63`). Reset trusts that result (`scripts/reset-training.ts:24`–`:29`), requires a business training marker, drops the named database (`:32`–`:48`) and then mints a marker for that name (`:53`). The baseline init schema had no name column, and the baseline claim only set `consumed_at` (`f3cb07db878d124029b6aa4a4533dfac482fb964:scripts/training/db-init/10-birth-token.sql:5`–`:10`; `scripts/training-birth.ts:38`–`:45` at that baseline).

**Concrete scenario — inference.** A cluster previously seeded A under R14 has a spent, nameless birth row. Another marked training business database B is restored/selected on that cluster. With the required maintenance privileges and training flags, reset of B passes the purported database-specific birth check and drops B, even though the row never identified B. This is an accidental-target safeguard gap, not an unprivileged remote reset. It does not affect the normal fresh-volume path after a new name-bound claim.

**Required correction.** Refuse legacy spent/unbound rows for reset, or require an explicit operator-established binding migration before destructive use. Preserve the intentional unused/unbound **first claim** separately. Until then, qualify the name-binding/reset claims for legacy state and follow the guide's fresh-volume requirement.

## Local single-Mac training decision

**Conditional GO for supervised fictitious exercises only**, provided the actual artifact and local isolation are established. Keep one operator responsible for seeding/reset; do not run overlapping maintenance or start a second attempt while a previous seed could resume. Use fresh dedicated training storage rather than relying on a legacy nameless birth row.

For the phone UI, use separate browser profiles for different training identities and avoid logout/re-login in the same live page as a handover mechanism. A profile holding pending photo work must stay with its training identity; close the old page/profile before switching people. If storage/network/logout work is stuck, stop that profile's exercise instead of continuing a new session over it. Use synthetic images and records only. These restrictions contain the findings for an exercise; they do not verify the logout or erasure guarantees.

No public publisher should be present or active for this local-only session. Do not follow the snapshot's obsolete Funnel publication steps. Do not infer local-only status from a successful startup check that also accepts an open proxy.

**Unrestricted shared-browser phone training/handover remains NO-GO until the lifecycle findings are corrected and evidenced.** Groups B/C remain outside this review and retain their separate acceptance obligations; this report neither approves nor reassesses T5 dispatch, the importer, real data, or general production readiness.
