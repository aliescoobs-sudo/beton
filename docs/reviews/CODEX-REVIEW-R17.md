## Findings

### R17-01 — HIGH — the validated image can differ from the image Compose executes

**Evidence:** `scripts/training-up.sh:12-15`, `scripts/training/dc.sh:7-9`, `scripts/training/ops.sh:8-10` validate the first literal `APP_IMAGE=` in `.env.training`. `dc.sh:9` then inherits the shell environment and passes a second env file. Both application and privileged ops images use Compose interpolation (`docker-compose.training.yml:38,83`). Shell variables take precedence over env-file interpolation, and later env files override earlier ones. This is documented by [Docker's interpolation specification and precedence explanation](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/).

**Failure scenario (source-derived, not executed):** the file contains an allowed digest, but the operator has exported a different/tagged `APP_IMAGE`. Startup announces acceptance of the file's digest, while pull/run/bootstrap/seed use the exported value. An `APP_IMAGE` in the later maintenance env file is another mismatch path. `dc.sh` also forwards general Compose arguments, so extra files/env arguments can replace the validated configuration. These are operator/configuration paths, not an unauthenticated HTTP exploit. Their importance is that privileged ops receives maintenance credentials under a misleading image-validation assurance.

`image-policy.sh:5-16` itself correctly fixes owner/package and requires 64 lowercase hex digits. It rejects the wrong input when that input is actually passed. It proves reference shape, not association with the reviewed commit. `running-image.sh:12` labels any reference of that shape an “accepted digest”; it does not compare to the configured or approved digest.

**Correction/test:** resolve and validate the effective app AND ops images, then bind that exact value to the subsequent invocation. Reject unsupported configuration overrides or explicitly validate their effective result. Test a good file plus a bad exported value, a conflicting second env file, duplicate keys and forwarded overrides. Use stubbed Docker and synthetic files; do not print resolved environments. Compare observed runtime image IDs/digests to an independently approved commit/digest/platform association.

### R17-02 — HIGH — plant isolation is incomplete at the database boundary and in dispatched payloads

**Write evidence:** `db/migrations/0208_roles_v1_hardening.sql:126-127` allows an event insert by any mapped `plant` actor with its own `created_by`, without checking the trip's plant. Cancellation INSERT/SELECT policies remain `0058_dispatch.sql:108-112`, also without trip scope. The new cancellation definer (`0208:83-95`) locks the trip and calls the internal, unscoped start check, but adds no scope authorization.

**Failure scenario (SQL inference):** an app-login transaction acting as manager A and knowing a trip UUID in B can cancel B's unstarted trip, or append the next correctly ordered event to B's started trip, even though SELECT of B's trip/events is denied. Cancellation also recreates a start oracle: an attempted insert succeeds for an unstarted live trip and raises the started-specific exception otherwise. A rollback does not undo the information learned. This needs app-login SQL capability; the inspected normal `recordTripStep`/reassign services first read their scoped target (`trip-service.ts:155-168`, `dispatch-service.ts:530-537`), so no direct ordinary HTTP insertion bypass is demonstrated. SQL guards were explicitly part of the required boundary.

**Read evidence:** `0082_roles_v1.sql:87-92,96-105` deliberately admits NULL-plant plans/orders to every manager. `dispatch-service.ts:269-299,314-320` returns their IDs, client/order/truck codes, quantities, planned times, driver name and override explanation along with `foreign: true`; the whole day is passed into a client component (`src/app/[locale]/(protected)/dispatch/page.tsx:156-160`). `listTrips` likewise returns the NULL-plant plan and driver identity even when its steps are hidden (`trip-service.ts:74-121`). `driver_read` is global (`0058:39-40`), driver is absent from the restrictive plant-table list (`0082:87-88`), and both `activeDrivers` and `listDrivers` read the global roster (`dispatch-service.ts:215-219,647-652`). **Impact:** “manager sees only own plant, including drivers and rotations” is not satisfied. An actually assigned B plan is filtered before `foreign` is calculated; adding that boolean does not newly reveal B's row through this query. NULL-plant history, the shared roster and cancellation rows are separate residual exposures. **Correction/test:** scope event/cancellation writes and reads by the referenced trip, preserve an explicit owner/app_admin path, and decide a restricted treatment for unassigned history and driver affiliations. Test app-login raw SELECT/INSERT and every normal/bulk/export path with A, B and NULL trips; verify unchanged B state and indistinguishable forbidden/nonexistent results. ### R17-05 — HIGH — another well-formed XML spelling bypasses 1904-calendar refusal

**Evidence:** `src/modules/importer/domain/sheet.ts:149` matches the start tag with `([^>]*?)`. A `>` within a quoted attribute truncates the attributes inspected at `:150-156`. Literal `>` is permitted by the [W3C XML AttValue grammar](https://www.w3.org/TR/xml/#NT-AttValue).

**Executed, fileless counterexample:** using the target `buildWorkbook` and `readXlsxSheets`, ordinary `<workbookPr date1904="1"/>` was refused. `<workbookPr codeName=">" date1904="1"/>` was accepted and returned the numeric date cell `45000`. The fixture existed only as an in-memory Buffer. No import or database was involved.

**Failure scenario:** the workbook's real 1904 flag follows such a string attribute. Import planning reads serial dates using the other calendar and can silently shift dates by 1462 days. Prefix/quote/entity improvements close the old examples, but the positive refusal is still bypassable.

**Correction/test:** use a bounded XML parser/tokenizer that understands quoted attributes, validates relevant namespaces/structure and fails closed for unsupported calendar declarations. Add this case with both quote styles, comments, prefixes and attribute order permutations; then reconcile synthetic downstream financial dates. Do not admit real workbooks to discover calendar errors.

### R17-06 — MEDIUM — footer wrapping trusts incomplete glyph widths; some accepted profiles still clip

**Evidence:** `src/lib/pdf/pdf.ts:98-112` falls back to 556 units for letters absent from its small Helvetica table. `Æ` and `Œ` are emitted as real WinAnsi glyphs (`:29-56`) but are 1000-unit Helvetica glyphs in the [Adobe Helvetica AFM distributed by PDFKit](https://raw.githubusercontent.com/foliojs/pdfkit/master/lib/font/data/Helvetica.afm). `wrapFooter` and horizontal placement both use the underestimated widths (`:130-162,276-279`); profile acceptance uses that same wrapper (`company.ts:62-74`). PDFs use the base font's actual widths (`pdf.ts:264-265`).

**Executed, fileless counterexample:** a schema-valid profile with a 200-character `Æ` legal name was accepted. The first footer line contained 132 such glyphs, measured by the application as 513.744 points at 7 pt; their actual advance is 924 points, exceeding the A4 page before the line finishes. Every invoice/statement/BL using this shared footer is affected. The claimed “all legal identity fully visible for every maximum valid profile” is therefore too broad.

**What passed:** all five supplied non-rendering test callbacks passed for the short, maximum ordinary-text and unbroken W/M examples, multi-page invoices/statements, BL and placeholder. `PdfLayout` now reserves the wrapped footer height (`layout.ts:26-30,41-45,120-124`), and every page gets the footer. This is a substantial correction of the original long-line bug. However, the test bounds are calculated by the implementation's own `textWidth` (`scripts/legal-footer-pdf.test.ts:81-85,99-102`), so they cannot detect this error. Its BL example is single-page; multi-page BL acceptance is not demonstrated.

**Correction/test:** use complete metrics for the exact encoded glyphs, or a font/measurement/rendering system with complete coverage. Independently render all pages of all three documents with maximum accepted registrations/address and supported ligatures/punctuation, and inspect ICE/RC/IF/address/legal name. Use renderer-derived bounds, not the same width function as both implementation and oracle. No PDF pixel rendering or actual legal/company acceptance was performed here.

### R17-07 — MEDIUM — legacy-photo migration can lose new old-tab captures or resurrect erased photos

**Evidence:** `src/modules/field/ui/photo-queue.ts:179-197` snapshots old rows and copies them in a separate database transaction; `:206-216` removes only those snapshot keys; `:223-234` then deletes the entire old database. There is no cross-database lock, migration epoch or session-generation check. `field-app.tsx:279-287` starts an independent migration through `queuedPhotos()` at mount; further reads/wipes also initiate migration (`photo-queue.ts:295-315`). The new module closes its own connections on versionchange, but cannot make a pre-rebrand page cooperate.

**Failure scenarios (inferred, not browser-reproduced):**

- After the snapshot, an old page adds another photo. The new code removes the copied keys and asks for whole-database deletion. When the blocking old page eventually closes, deletion can remove a photo never copied. A `blocked` notice is useful but is not a guarantee of preservation.
- Migration A reads a legacy photo, then pauses before writing the new store. Migration/wipe B copies it, erases it for logout/account switch and finishes. A resumes and puts its cached row back into the new store. Its old sequence is not a fence against a put occurring after the wipe. The independent startup migration makes this possible without the guarded capture path authorizing new work.

**Account boundary:** the copy does retain `userId` (`:191`), and upload/counting paths filter by current owner (`field-session.ts:128-142,223`). The server's photo door verifies the trip's driver (`0098_driver_bl_photo.sql:57-63`). No demonstrated A-photo upload under B's account is claimed. The failures are persistence/erasure and preservation failures; same-origin storage after handover must not be certified erased.

**Correction/test:** fence legacy writers first, serialize migrations and wipes across pages, and make wipe tombstones/epochs effective against delayed copies. Do not delete rows that were not included in a committed copy. Add deterministic pauses after snapshot and before copy commit, concurrent logout and account switch, and an old tab writing after the snapshot. Verify both stores after every stage and after all tabs close, in real browsers.
