## Findings, ranked by severity

### R21-01 — MEDIUM — Failed status query can silently leave the old Basic credential active

**Introduced path and evidence:** after publishing the replacement hash (`scripts/staging/make-basic.sh:67–70`), the script runs `dc.sh ps -q proxy 2>/dev/null || true` at `:73`. An empty result enters the “proxy is not running” branch at `:77–79`, regardless of whether the query succeeded. The script then exits successfully. `docs/STAGING-VPS.md:208` promises automatic recreation with no further action.

**Trigger:** rotate on an already running staging proxy while the status wrapper fails before returning an ID: for example, an inherited override is refused, the approved checkout check fails, or Docker/Compose's status request fails. Docker live-restore can leave the existing proxy serving while daemon control is unavailable (`docs/STAGING-VPS.md:276`). The earlier hash-generator Docker call can succeed and the later status call fail; these are separate operations.

**Impact:** the disk hash changes but Caddy's loaded configuration still accepts the old password. The operator receives success and a false “not running” explanation during attempted revocation. A directory mount makes new bytes visible; it does not reload Caddy. There is no demonstrated unauthenticated window, but a holder of the old Basic credential can retain that layer of access. If recreation itself fails, `:76` does return failure, but can likewise leave the old instance active depending on where failure occurred.

**Fix:** distinguish failed status lookup from a successful empty lookup and return nonzero with “rotation not applied/old credential may still work.” Require validated recreation and health confirmation when an instance exists. Preserve an explicit incomplete-rotation result on failures after publication; do not promise revocation merely because the file was replaced.

**How to verify:** make the hash-generator call succeed, then fail only the status query while a previously configured Caddy continues running. Require nonzero helper exit and no “not running” success claim. A real successful rotation must reject the old password and accept the new password over HTTPS. Separately inject a recreation failure and require an incomplete-rotation result. The current test at `scripts/staging-config.test.ts:356` only looks for the recreation command as text; the integration rotation fixture does not exercise this branch (`tests/staging-proxy-readability.int.test.ts:48–63,148–170`).

**Staging disposition:** nonblocking for the documented reset/start move to this commit. Must be fixed before relying on unattended/helper-reported credential revocation. Until then, explicitly verify the new/old credential outcomes and treat any status/recreate uncertainty as incomplete rotation.

### R21-02 — LOW — Value-taking `up` options can bypass all hash/directory checks

**Inherited defect, newly relevant to the extended guards:** `scripts/staging/dc.sh:65–70` counts every non-dash argument as a service name instead of parsing option values. The same logic exists at T10h `scripts/staging/dc.sh:65–70`; this commit did not introduce it.

**Trigger:** an operator invokes, for example, `./scripts/staging/dc.sh up -d --wait --wait-timeout 60` with no explicit service. The loop counts `60` as a service, never sees `proxy`, and leaves `needs_gate=no`. Compose consumes `60` as the option value and starts the default services, including proxy. Thus `dc.sh:80–91` is skipped even though a proxy can be created. This is source reasoning, not an executed reproduction.

**Impact:** a readable but wrongly owned, writable or symlinked gate/directory can reach proxy startup despite the claimed wrapper policy. Missing/unreadable mandatory imports still make Caddy fail; this alone does not make the normal Caddyfile serve without Basic Auth. Exploitation of writable configuration also needs local write access and the operator invocation. The official `up.sh:43` uses `up-proxy`, which unconditionally selects the checks, and the new recreation command explicitly names `proxy` (`make-basic.sh:76`).

**Fix:** parse/allow-list `up` options with their values, or conservatively require gate validation for every `up` except a narrowly validated explicit db/app-only form. Keep the first database-only start possible.

**How to verify:** exercise `up` with separated and equals-form option values, no service, explicit proxy, and explicit db/app controls. With an unsafe gate, every invocation capable of starting proxy must fail before the container-creating Compose call. The present tests cover only plain bare `up -d` and explicit db (`scripts/staging-config.test.ts:559–561`).

**Staging disposition:** nonblocking for the mandated `up.sh` path on the single-admin host. Do not interpret the wrapper's general “before any proxy start” claim as proven.

## Directory, permission and disclosure boundaries

The new mount is an exposure of all present and future entries to the proxy filesystem, not a whitelist of one hash. Besides the two tracked documentation/example entries, the helper creates the final hash and an unpredictable temporary file in that directory. It creates the temporary under `umask 077`, fills it, changes it to 0644, then renames it (`make-basic.sh:17,56–68`). Its EXIT trap cleans a failed temporary during ordinary failure. SIGKILL, host failure, or a failure after chmod but before rename can leave a 0600 or 0644 hash-only temporary. No plaintext password is written there by the inspected helper, and it makes no historical backup. The entire directory, including such remnants, is mounted; no code rejects unrelated files. Keep backups, exports and other secrets out of it. Gitignore at `.gitignore:37–39` prevents accidental tracking of the intended final/temp names, not runtime exposure of arbitrary entries.

The Caddyfile has one explicit external application proxy after the exact hash import, a loopback health responder and a catch-all HTTP 404 (`Caddyfile.staging:60–106`). There is no `file_server`, filesystem root, wildcard import or handler that returns other directory contents. A URL resembling `/etc/caddy/staging/...` is an application request behind Basic Auth, not a mapping to this mount. README/example/temp/backup entries are not automatically imported or served. A compromised proxy process could read any additionally readable mounted files; read-only mounting prevents writes from that mount but is not confidentiality isolation. Syntax errors in deliberately modified imported configuration could reach Caddy diagnostics; “nothing can ever appear in logs” cannot be guaranteed for arbitrary operator-supplied configuration or the external Caddy binary. No such disclosure path was found for helper-generated content.

The answer to “write any secret” is not an absolute no: the helper intentionally writes the bcrypt hash to the temporary/final file. Also, `up.sh:17–21` invokes the unchanged provisioning/seed path, whose one-time training credentials are intentionally written in the separate accounts volume (`docker-compose.staging.yml:159,163–165,181–182`; `docs/STAGING-VPS.md:220–225`). T10i adds no copy of those credentials to the proxy directory or new secret-bearing journal field. These existing credential files and actual journals were not opened. The normal new diagnostic code never reads hash contents for output; `up.sh:43` and `make-basic.sh:76` still allow the external Compose command's own stdout/stderr through, so the source review cannot establish a universal no-leak guarantee for external executable failures.

For `up-proxy`, static symlinks at either `staging` or the final hash, nonregular final objects, wrong UID, group/other write bits, missing other-read on the hash and missing other-traverse on the directory are refused (`dc.sh:77–91`). Checks are semantic permission-bit checks, **not exact mode equality**: 0444 is intentionally accepted by the test (`staging-config.test.ts:524–527`), and the code permits other harmless read/execute combinations. It does not test hard-link count or strictly parse the complete Caddy snippet; the two grep predicates at `dc.sh:91` are only a shape check. A deploy-owned configuration file remains trusted executable Caddy configuration, outside the commit's content binding.

The symlink/stat/grep checks and Docker mount are separate pathname operations, so there is a TOCTOU interval. Directory owner-only write and a trusted parent checkout prevent an ordinary different-UID local user from replacing the entries during it. The guide provisions `/srv/kayas` as deploy-owned 0755 under `/srv` (`docs/STAGING-VPS.md:111–125`); that parent-directory trust remains essential. A process running as deploy, root, or a principal able to rename the parent can still race/repoint the mount or replace the imported configuration after validation. Deploy already has root-equivalent Docker access (`docs/STAGING-VPS.md:74,90`). No race-free boundary against that principal is supplied or claimed by this review. Extra symlinks are not automatically followed/imported, and symlinks read inside the directory mount resolve within the container's namespace, not to arbitrary unmounted host files.

`validate-compose.py:26–29,126–136` accepts read-only binds whose sources end with `/staging` and have the expected target. It does **not**, independently, reject `/some/other/staging`, require every expected bind, or establish realpath/inode identity. Named volumes/tmpfs also receive no equivalent target restriction there. These are inherited validator limitations. In the authorized path, Compose has a literal `./staging` source, a fixed `-f` and env-file list (`dc.sh:59`), shell/Compose/context overrides are rejected (`dc.sh:14–23`), tracked edits/wrong HEAD are rejected (`release-lib.sh:74–82`), and run-time mount options are denied (`release-lib.sh:93–114`). No T10i input was found that changes that literal source through the normal wrapper. The validator alone is not proof of absolute mount-path binding, and filesystem replacement by the trusted deploy principal remains possible.

The README was not updated: `staging/README.md:3–5` incorrectly says only the README is tracked and still describes mode 0600. Decision 228 and the deployment guide supersede it. Correct it in a follow-up to prevent recurrence of the availability fault; this is not an extra authentication bypass.

## Test assessment and CI limits

The strongest new test uses the actual helper, copies its result and mode into a named Docker volume, changes ownership to a foreign UID, and invokes real `caddy validate` with `--cap-drop ALL`, `--cap-add NET_BIND_SERVICE`, `--read-only`, `no-new-privileges:true` and read-only config/hash mounts (`tests/staging-proxy-readability.int.test.ts:48–145`). This distinguishes the Linux ownership problem from macOS bind-mount behavior. The 0600 negative control explicitly requires “permission denied”; the positive checks require a readable/nonwritable helper-generated file and successful real configuration validation. Against the T10h helper, the world-read assertion at `:139` fails; the unchanged 0600 negative control should still succeed. This comparison is established by source, not by running old/new versions here.

The permission probe uses the same security flags relevant to the reported failure as Compose (`docker-compose.staging.yml:21–24,103–110`). It does **not** start a listening Caddy service: it runs `caddy validate`. It substitutes tmpfs for the persistent `/data` volume and omits service networks, published ports, resource/log limits, restart and health behavior. It therefore proves configuration readability/provisioning under those flags, not the entire production-shaped proxy lifecycle or TLS/authentication over HTTP.

Specific weak assertions and limits:

- The directory-rename test runs `sleep 120` in an unconfined image and reads the file with `cat`; it proves new file visibility, not Caddy reloading or accepting/rejecting credentials (`staging-proxy-readability.int.test.ts:148–170`). Its fixture omits the env/wrapper that enables the helper's recreation branch. It does not test R21-01. It can pass with the old helper when paired with this test's directory mount; the static Compose assertion is what distinguishes the old single-file Compose mount.
- `staging-config.test.ts:352–367` checks command/flag strings, not execution equivalence. Its description says the wrapper accepts “exactly” 0644, but its own later test intentionally accepts 0444. The wrong-owner test changes `id` for both directory and file, so it fails at the directory check and never independently exercises the file-owner branch (`:529–534`). Static symlink and mode cases otherwise have meaningful refusal checks (`:507–558`).
- `staging-up-proxy.test.ts:12–25,61–93` runs the real shell script against command stubs. The new permission diagnosis and post-start readability/health/restarting assertions would fail against T10h's `up.sh`; the healthy control would pass both. The secret-output assertion checks that one synthetic “Could not import” log line is not echoed, without a hash/password canary. It does not prove external Caddy/Compose can never emit secrets, and the stub does not verify the exact `test -r` expression. No new test here performs a real forced recreation and credential revocation check.

CI scheduling is present: `vitest.config.ts:29–31` includes the script tests in unit, `:37–43` includes this integration file, `build-image.yml:36,40–46` requires both projects, and `integration.yml:58` runs the integration project on Ubuntu. The new integration suite skips without Docker **only outside CI** and installs a failing test when Docker is absent in CI (`staging-proxy-readability.int.test.ts:14–34`). The config unit suites still conditionally skip without Python/Compose (`staging-config.test.ts:19–31,163,371`), and the older unconfined adaptation check silently returns if the Caddy image is absent (`:238–240`). The `up.sh` unit tests have no conditional skip. Thus the main new permission regression is not silently optional in CI, but not every auxiliary Docker/Python assertion is enforced unconditionally. No actual CI result for this target was inspected; “passes now” remains an author claim, not independently executed evidence.

The new `auths` grep (`docs/STAGING-VPS.md:140–142`) avoids printing credential content and fixes the mistaken count of the word `auths` for the stated default Docker setup. It also only prints a warning rather than stopping the pasted command block. A stronger follow-up would parse JSON without printing values and account for any configured credential helper. No helper configuration or stored credential was inspected here; do not infer a remaining live token from this limitation.
