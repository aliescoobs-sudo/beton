## 2. Scope A — bypass examination

### Birth token, emptiness, reset and replay

**Verified in source:** initdb creates `postgres.public.volume_birth`, revokes PUBLIC privileges and inserts its sole row ([scripts/training/db-init/10-birth-token.sql:5](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/scripts/training/db-init/10-birth-token.sql#L5)). The helpers connect as the maintenance superuser to the **postgres maintenance database**, not to the business database ([scripts/training-birth.ts:15](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/scripts/training-birth.ts#L15); [scripts/db-bootstrap.ts:53](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/scripts/db-bootstrap.ts#L53)). Neither runtime login is granted this table. A random token value is generated, but the admission decision never checks that value against an external secret: it tests for an unused row and atomically sets `consumed_at` ([scripts/training-birth.ts:26](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/scripts/training-birth.ts#L26), `:38`).

- **Forgery:** an ordinary web/phone account has no discovered path to mint it. A cluster superuser, owner of this table, or someone able to restore the maintenance database can manufacture/reset the row. It is a protected, consumable cluster marker, not a signed token or external attestation.
- **Claiming twice:** concurrent ordinary claims on the same singleton row cannot both update an unused version. A failed seed still spends its claim; no refund exists. This favors refusal and can require rebuilding the training volume. No token-based bypass of the exact business-table check was found.
- **Dump/restore:** an ordinary dump of only the business database does not carry the separate maintenance table. Restoring nonempty business tables into a fresh token-bearing cluster still fails the exact emptiness check. Conversely, a maintenance-database dump, whole-cluster dump, or physical snapshot can carry an **unused** row; restoring pre-consumption state replays it. A completed business dump can also carry `training_marker`; seed returns early for a marked database and startup checks that marker, not birth provenance ([scripts/seed-training.ts:208](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/scripts/seed-training.ts#L208); [src/lib/training.ts:24](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/src/lib/training.ts#L24)). Thus the broad “restored databases cannot pass” claim is too strong.
- **What reset permits on a nonempty database:** `wipeTrainingDatabase` first requires the training marker, then **drops the entire selected business database WITH (FORCE)**, recreates it and only then mints a cluster token ([scripts/reset-training.ts:15](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/scripts/reset-training.ts#L15), `:31`, `:35`). It does not grant permission to seed over a nonempty unmarked database. A nonempty marked training database is deliberately destroyed and replaced. The marker does not distinguish legitimate training rows from any unrelated rows an operator later put there. The helper itself does not check mode flags; the CLI does (`:56`). It also does not require an existing birth row, so a restored marked database can be reset on a cluster that never had one. Other nonempty databases on that cluster are neither inspected nor dropped, and the minted row is not bound to a database name.
- **Test escape:** [scripts/training-birth.ts:70](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/scripts/training-birth.ts#L70) checks only an allowlisted database basename; it does not require NODE_ENV or a runner signal. The deployed CLI supplies no provenance override, so no deployed flag bypass was found. A trusted programmatic caller can skip provenance on any cluster using an allowlisted name. This is narrower than arbitrary-database admission, broader than proof that an actual test runner owns the database.

**Exact emptiness limits:** zero main-fork size is physical metadata, not resettable statistics; RLS cannot manufacture a zero size. A written, nonzero-size heap hidden by RLS fails even after ordinary deletion. Zero size does **not** mean “never written”: TRUNCATE or physical rewrites can remove pages. The scan is not locked together with all subsequent seed writes, so maintenance must exclude concurrent business writers. Partitioned parents are accepted without a read; children in public/finance are separately scanned, but a partition moved outside those schemas would evade enumeration. No such partitioned business table was found in the stock reviewed schema. These limits do not restore R13's statistics bypass. PostgreSQL documents [relation-size functions](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADMIN-DBSIZE) and [RLS owner/FORCE behavior](https://www.postgresql.org/docs/17/ddl-rowsecurity.html).

### Reservation-column semantics

**Verified in source:** `identifier_hmac` is `bytea` constrained to 32 bytes ([db/migrations/0004_auth.sql:82](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/db/migrations/0004_auth.sql#L82)); `keyedHash` supplies the same representation for a reservation as for other entries. Office identifiers/IPs use `id:`/`ip:`; field reservations/IPs use `fieldres:`/`fieldip:` ([src/modules/platform-security/auth/login-guard.ts:38](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/src/modules/platform-security/auth/login-guard.ts#L38), `:98`, `:105`). No cast of the reservation to a user ID or reliance on an email-column meaning was found. `releaseFieldAttempt` does not validate existence/ownership itself, but only the login handler supplies its server-held reservation; the request body cannot choose it. A wrong-IP release cannot match, a duplicate release is just another EXISTS match, and a late release does not offset a new UUID. Cross-namespace HMAC collisions or random UUID collisions are cryptographically negligible, not a practical release bypass. An attacker with arbitrary auth-pool writes is outside this boundary. No new migration is necessary for storage type correctness, although an explicit attempt kind would make future maintenance less error-prone.

**R14-01 — T5: started-state checks and dispatch writes are not one serialized decision.**

**Verified in source:** reassign/postpone read live state without a shared plan lock ([src/modules/operations/service/dispatch-service.ts:430](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/src/modules/operations/service/dispatch-service.ts#L430), `:496`). “Started” means a row in `trip_event` (`:221`, `:497`), ignoring the driver's `loading_started` report, which is stored separately ([db/migrations/0118_trip_timing.sql:171](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/db/migrations/0118_trip_timing.sql#L171)). The cancellation trigger checks only events and does not take the event writer's advisory lock ([db/migrations/0059_trip_tracking.sql:54](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/db/migrations/0059_trip_tracking.sql#L54), `:83`). New plan identity is unique only within a random batch ([db/migrations/0058_dispatch.sql:74](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/db/migrations/0058_dispatch.sql#L74)). Overlapping drivers/trucks are warning conflicts, not blockers ([src/modules/operations/domain/dispatch.ts:93](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/src/modules/operations/domain/dispatch.ts#L93)), and the new reassign action discards returned conflicts ([src/app/[locale]/(protected)/dispatch/actions.ts:79](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/src/app/[locale]/(protected)/dispatch/actions.ts#L79)).

**Failure scenarios:** a manager can move/postpone a rotation after its driver reported loading begun, even without concurrency. With concurrency, the cancellation guard can observe no event while the event guard observes no cancellation; both then commit, leaving a cancelled yet loaded/started rotation. The global audit lock is acquired by the AFTER audit trigger, after these BEFORE checks; it does not revalidate them. Two saves that initially see no unstarted plan can also insert independent batches for the same work. The unique cancellation row should defeat two replacements that both cancel the same existing plan; it does not cover those other cases. A reassignment can additionally double-book a driver on another truck and return success without presenting the warning.

**Correction:** serialize cancellation, starting and replacement under the same day/resource/trip locking discipline; include loading reports in the started predicate; re-read state after locking. Decide and enforce the overlap policy, and surface any accepted conflicts in the new action. Training containment: one dispatcher at a time; never use these assignments to control physical work.

**R14-03 — Scope C: COMMIT/ROLLBACK failures are swallowed and success is reported before durable commit.**

**Verified in source:** `importWorkbook` sets `report.applied = true` before the final `COMMIT`, whose rejection is suppressed ([src/modules/importer/service/workbook-import.ts:209](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/src/modules/importer/service/workbook-import.ts#L209), `:215`). Soft rollback does the same suppression (`:363`). The report describes an applied run or completed rollback based on those pre-commit values ([src/modules/importer/service/report.ts:11](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/src/modules/importer/service/report.ts#L11), `:50`). Connections are released normally even if transaction termination failed.

**Failure scenario:** a commit-time constraint error rolls the transaction back, but the CLI reports IMPORT DONE and exits successfully; a connection failure makes the commit outcome unknown while still reporting success. A rejected rollback is likewise presented as guaranteed dry-run cleanup. If a live transaction survives a cleanup failure, returning that connection to the pool can contaminate later work; this last consequence depends on the particular database/connection failure. PostgreSQL still provides transaction atomicity; the defect is untruthful success/cleanup assurance, not evidence of an ordinary partial COMMIT.

**Correction:** await successful commit before marking/reporting applied; propagate failure with a safe error code and distinguish an unknown outcome. On failed transaction cleanup, destroy the connection. Apply the same rule to soft rollback. Verify commit-time failure and connection-loss outcomes before using real files.

**R14-04 — Scope C: the XLSX reader silently assigns dates using the wrong workbook calendar.**

**Verified in source:** workbook metadata is used for sheet names/relationships but not `workbookPr.date1904` ([src/modules/importer/domain/sheet.ts:97](https://github.com/aliescoobs-sudo/beton/blob/f3cb07db878d124029b6aa4a4533dfac482fb964/src/modules/importer/domain/sheet.ts#L97)); the date decoder always uses the 1899-12-30 origin (`:239`). Microsoft documents the [XLSX Date1904 attribute](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.workbookproperties.date1904) and the [two date systems](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-xls/4a5e900a-0eb0-4355-8fc1-81aab8f46e8b).

**Failure scenario:** an otherwise valid workbook using the 1904 calendar imports cheque dates, price effective dates or recipe dates 1,462 days early. Both dates can be within the accepted range, so dry run and apply succeed with the same wrong interpretation. The report shows counts rather than interpreted dates, making this hard for an operator to notice.

**Correction:** honor the workbook calendar or refuse unsupported calendars before processing cells. Further strictness gaps verified in the same reader: duplicate accepted headers silently select the first column (`:266`); malformed CSV with an unclosed quote is accepted (`:175`); formulas' cached `<v>` values are treated as ordinary values (`:141`). Reject ambiguous header mappings/malformed files and explicitly define the cached-formula policy. Decimal/date lexical validation alone does not establish spreadsheet fidelity.
