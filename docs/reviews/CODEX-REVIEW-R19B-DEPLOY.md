## Findings

**R19B-01 · HIGH · No executable staging deployment with Basic Auth.**  
`Caddyfile:5–12`, `docker-compose.prod.yml:28–39,47–60`, `docker-compose.training.yml:64–79`, `docs/checkpoints/CP-TRAINING.md:138–149`. **Trigger/access:** an operator follows the production runbook or training’s public-profile instructions. Neither proxy config implements Basic Auth; all forwarded pages, APIs, phone endpoints and assets reach the application without the requested outer gate. Production forces `REAL_DATA=true`; enabling training there fails environment validation. The training public profile uses the same unauthenticated Caddyfile, with password-only training identities. The VPS paragraph also omits bootstrap/seed sequencing and places DNS after proxy startup.  
**Fix:** provide one reviewed staging configuration and ordered runbook: production build, `APP_ENV=training`, training ON, real data/simulation OFF, fresh dedicated seed, exact HTTPS origin, and hashed Basic credentials enforced on the entire application vhost. Keep application authentication and TOTP. Do not publish before that configuration exists. **Verify:** without/wrong Basic credentials, page, RSC, static, auth, field and mutation requests never reach Next; valid Basic credentials still require the application session. Check domain/IP/alternate-port bypasses and certificate issuance.

**R19B-02 · HIGH · Production does not bind privileged execution to the approved image.**  
`scripts/ops/dc.sh:7–10`, `deploy.sh:14–15,25–59`, `ops.sh:7–9`; `docker-compose.prod.yml:65–95`; `docs/RUNBOOK.md:30–35,65–71`. **Trigger/access:** operator shell containing an exported `APP_IMAGE`, mutable tag in the env file, or additional Compose configuration. The production wrapper passes through arguments/environment and performs none of training’s effective-image validation. Shell `APP_IMAGE` can override the value deploy writes: the pulled/logged digest differs from the image receiving app, migrator and bootstrap credentials. A digest’s shape alone also does not establish its reviewed commit/publisher. Unqualified `git pull` can move host scripts/configuration independently.  
**Fix:** reuse strict configuration/effective-service checks for app, ops, bootstrap and backup; reject overrides, tags and unapproved registries. Record reviewed commit, workflow result, approved digest/platform and actual container identities for every privileged job. Pin host scripts/config to the same approved release. **Test:** hostile shell image, duplicate/env/Compose overrides and mismatched commit/digest must refuse before credentials reach a container. Training’s picker/evidence mechanism is useful, but production does not invoke it.

**R19B-03 · HIGH · Twin-only assurance remains incomplete.**  
`src/modules/importer/history/domain/guard.ts:33–57`, `service/read-set.ts:123–139`, `service/history-import.ts:239–245,303–325` under the same history module. **Trigger/access:** operator imports a marked workbook containing real/private content in an observation or legacy field, or an admin corrects staged cells. The guard checks selected names/vocabulary, not every retained effective value. A marker does not prove fictitious origin. This carries forward R19-03; T11b does not repair it. The new mount accepts any existing absolute directory (`scripts/training/ops.sh:46–52`), not an authenticated twin set.  
**Fix:** validate the complete effective twin set, including corrections; restrict the mounted directory to a dedicated reviewed generated set. Until repaired, disable server-side history importing and provision only an independently verified generated fixture. **Test:** canaries in omitted fields and post-stage fixes must refuse before any staging/apply write. Never mount the owner’s home or real-data directories.

**R19B-04 · MEDIUM · Documented secret entry can echo or enter shell history.**  
`scripts/ops/ops.sh:9`, `scripts/training/ops.sh:69`, `scripts/prompt.ts:13–18`, `scripts/create-owner.ts:25–26`, `docs/RUNBOOK.md:37,40,61`. **Trigger/access:** an operator types owner credentials/TOTP through the `-T` wrapper, or substitutes actual secrets into the runbook’s literal shell commands. Without a container TTY, the prompt uses ordinary stdin; a human terminal can echo the secret. Literal backup URLs and key assignments can persist in shell history. The bootstrap example also creates the secret file before the wrapper later applies mode 0600.  
**Fix:** explicit interactive TTY mode with hidden input, batch mode only for securely supplied stdin; create/edit secret files privately from their first byte with `umask 077`. Keep secrets out of command arguments/history and session recordings. **Test:** real pseudo-terminal owner/import/recovery flows must not display canaries; inspect creation modes under umask 022. Linux GHCR credential-helper/storage, PAT expiry/revocation and the deploy account’s Docker config also need instructions.

**R19B-05 · MEDIUM · Host port verification can report success on failure/exposure.**  
`scripts/ops/verify-host.sh:13–15`. **Trigger/access:** Docker inventory fails, a container publishes on a specific public IP, or one container publishes both 80/443 and another public port. Errors become an empty list; only wildcard publications are inspected; the final grep discards an entire line containing an allowed port, including other forbidden ports on it. This is a false assurance, not evidence that the stock database is published.  
**Fix:** fail closed on inventory errors and inspect every published address/port individually, including IPv6 and explicit host addresses. **Test:** failed Docker query, explicit public binding and mixed allowed/forbidden bindings must fail. Retain an independent external all-port scan; the runbook’s limited port list misses other listeners.

**R19B-06 · MEDIUM · Backup verification/pruning conflicts with host ownership.**  
`scripts/ops/init-host.sh:16–20`, `backup-nightly.sh:10–17`, `deploy.sh:37`. **Trigger/access:** the documented non-root deploy account runs deployment/nightly backup. Backups are owned by uid 10001 in a mode-2750 directory; only the puller is added to its read-only group. The deployer may not list/read them, and even group membership grants no directory write permission for host-side pruning. Backup container creation can succeed before the host script fails. After retention fills, pruning fails; deployment aborts before switching.  
**Fix:** run verification/pruning in the uid-10001 backup container or a narrowly specified privileged service, preserving puller read-only access. Specify cron identity, PATH and alert setup. **Test:** actual Linux users/groups, more than 14 sets, a successful deploy-triggered backup, and denied puller deletion. Stub/text tests do not prove these permissions.

**R19B-07 · HIGH · Recovery instructions do not recover a replacement server.**  
`docs/RUNBOOK.md:60–62,85–88`, `scripts/ops/backup-pull.sh:18`, `scripts/restore-test.ts:33–41`, `scripts/backup-lib.ts:505–535,618–621`. **Trigger/access:** operator performs the documented monthly restore or loses the VPS. Pull defaults to the office’s home backup store, whereas the printed restore command defaults to checkout `backups/`. The restore checker intentionally destroys its scratch database/files afterward; it is not a recovery/promotion command. “Restore, then switch” omits role bootstrap, exact release/tools, secrets escrow, destination ownership, volume import, cutover and verification. Training’s backup is database-only (`scripts/training-backup.sh:11–17`), unsuitable for recovering staging attachments and encrypted fields on a new host.  
**Fix:** explicit office manifest path and a rehearsed replacement-host procedure restoring database, filestore and versioned application keys together, with a preserved verified destination and rollback/cutover steps. Specify office Node/PostgreSQL/age tools and local scratch-role bootstrap. **Verify:** from an off-host signed set and sealed escrow, recover a disposable new host and open actual referenced fixture documents, sign in, verify audit/readiness and recover after reboot. The library’s real backup tests do not establish this operational rehearsal.

**R19B-08 · MEDIUM · Rollback is announced without verifying recovery.**  
`scripts/ops/deploy.sh:40–48`, `docs/RUNBOOK.md:71`. **Trigger/access:** migration/start/readiness fails and the old image also fails to start or become usable. The script prints “rolled back” even after the old start returns an error, and never polls its readiness or public route. Partial post-migration work can remain: `scripts/db-migrate.ts:27–37` performs additional steps after migration application. No deploy mutex or durable interrupted-deployment journal exists.  
**Fix:** serialize deployments; record switch state; verify old readiness/public behavior and report recovery failure unambiguously. Rehearse each schema’s backward compatibility and process/disk failure recovery. **Test:** real old/new images, committed migration followed by failure, failed old start, rollback readiness failure, concurrent deploy and process death. `scripts/server-hardening.test.ts:334–341` checks stub calls only. Migration-ahead readiness is intentionally allowed (`src/app/api/health/ready/route.ts:25–28`), checked, no issue.

**R19B-09 · MEDIUM · Several maintenance instructions cannot execute as written.**  
`docs/RUNBOOK.md:48–50,55,80`, `docker-compose.prod.yml:78`, `scripts/ops/init-host.sh:19`. **Trigger/access:** operator initializes mappings through ops. `imports/` is mounted read-only, so `--init-mapping imports/mapping` cannot write; host imports ownership also gives the deployer no ordinary upload right. History guidance specifies a folder outside the checkout but supplies no corresponding production mount/command. The owner-recovery instruction diverts to host package scripts, although the generic ops wrapper can already invoke both reset scripts.  
**Fix:** exact host-side private upload/mapping and read-only execution paths; a writable dedicated report output; interactive maintenance commands from the approved image. **Test:** fresh-host dry-run/stage/apply/rollback and owner recovery as the deploy user. T11b tolerates missing history report storage (`scripts/import-history.ts:67–73`); T2 still requires writable `.logs` (`scripts/import-excel.ts:77–79,185–188`), so an image built without that directory can fail before apply.

**R19B-10 · MEDIUM · Integration CI does not gate published images.**  
`.github/workflows/integration.yml:6–10,19–59`, `build-image.yml:40–42`. **Trigger/access:** ordinary push/tag/manual build. Integration is a separate workflow; image publication needs only its own lint/type/unit job. A failing or cancelled integration run can coexist with a successful publish/picker result; tag/manual builds need not have a matching integration run.  
**Fix:** make required integration a dependency of publication, or enforce an exact-commit release check before approving a digest. Keep e2e/manual release evidence separate. **Test:** deliberately failing integration prevents approval/publication for that commit. PR workflow permissions are read-only with generated disposable credentials and no referenced production secrets, checked, no issue. No apt fallback appears in this target: tool installation failures fail the job. External actions/tool repositories remain supply-chain inputs.

**R19B-11 · MEDIUM · Ordinary training shutdown leaves the LAN relay listening.**  
`scripts/training/lan-up.sh:29–40`, `scripts/training-down.sh:5`, `scripts/training/dc.sh:36`, `scripts/training/lan-relay.mjs:23–35`. **Trigger/access:** operator runs the usual training stop after LAN use. Compose stops Caddy, but the host relay survives. If another service later binds loopback port 8443, the lingering relay forwards LAN clients to it. There is no connection-count cap; private clients can also hold many sockets for ten minutes.  
**Fix:** make ordinary shutdown terminate and verify the relay, use managed process ownership, fail closure checks, and cap concurrent connections. **Test:** stop normally, assert no host listener/process, then bind a harmless loopback fixture and prove it is unreachable through the old LAN address.

**R19B-12 · LOW · Twin decision helper changes unrelated staged exercises.**  
`scripts/training-twin-decide.ts:49–78`. **Trigger/access:** authorized operator runs the helper while multiple sets have pending decisions. It selects all pending labels and discards all open quarantine returned by the service, without a batch/set selector or twin validation. It can discard another exercise’s pending work. This is not a production-role bypass: the training-mode/account guards are present.  
**Fix:** explicit verified set/batch scope and preview counts, refusing unrelated pending staging. **Test:** two distinct staged sets; selecting one must leave the other’s quarantine unchanged.

## Ordered prerequisites before the first Compose up on the VPS

These require corrected staging artifacts; the current target is not a copy-and-run procedure.

1. **Approve one release:** close/contain the blocking findings, select the reviewed commit, require matching green build/integration results and release tests, and record commit → approved image digest/platform. Pin host files and third-party images. Inspect the built image for excluded secrets/data and test sources. Do not use unqualified `git pull` as approval.
2. **Choose fresh staging storage:** dedicated project, database, filestore, accounts and Caddy volumes; no iMac database restore, production keys, credentials or real files. Establish that the volumes are genuinely new. Keep G1–G12 open for later real data.
3. **Provision access safely:** patched Ubuntu 24.04, working provider console, non-root deploy account and owner SSH public key. Verify a second key-only session before applying root/password-login denial. Install/enable Docker/Compose and document root-equivalent Docker access; do not expose its API.
4. **Set network policy:** provider firewall and host rules for admin-source SSH and TCP 80/443 only, both address families. Check Docker-aware filtering, no other listeners/publishers or forwarding. Keep LAN/public helper profiles disabled until the intended gate is ready.
5. **Set host budgets:** verified time sync, unattended upgrades/reboot plan, optional fail2ban, sufficient disk/RAM, chosen swap policy, Docker log rotation, resource/request bounds and working disk/OOM/readiness/backup alerts. No build on the VPS.
6. **Prepare DNS/TLS:** A record to the VPS; publish AAAA only if IPv6 actually works. Check 80/443 availability and outbound CA/DNS access; preserve Caddy state. Decide the HTTPS origin before generating env files. Never fix certificate errors by disabling secure cookies/TLS.
7. **Install approved host artifacts and registry access:** checkout the pinned release; configure private GHCR read-only access under the correct deploy account using protected credential storage. Pull approved digests and verify platform/image IDs. Keep PAT values out of history/logs.
8. **Create private configuration:** directories with documented owners; secrets created under umask 077, env files 0600. Training ON, `APP_ENV=training`, real data/simulation/test escapes OFF, exact HTTPS origin and one direct trusted proxy hop. No provider/VAPID credentials; maps/AI/extraction OFF. Use separate app/ops/backup secrets and URL-safe database passwords. Escrow versioned keys off-host.
9. **Install the staging Basic gate:** reviewed full-vhost configuration, strong independent credentials stored only as password hashes at Caddy, no application path exemptions. Validate configuration offline/in a disposable rehearsal; plan phone/browser/service-worker behavior and HTTP/API negative checks. Only ACME’s required challenge handling may be outside the application gate.
10. **Prepare backup/recovery before there is state:** office age/signing keys and sealed application-key escrow, fixed source/destination paths, restricted pull account, corrected backup/pruning identity and working alarms. Rehearse a signed database+filestore+keys recovery on a disposable host; define staging reset versus preserve-state policy.
11. **Prepare a generated twin only:** dedicated read-only directory, reviewed generator/manifest and complete-content checks; no real-data mount. Enrol owner/admin TOTP through the protected HTTPS app before any apply. Specify interactive image-based dry-run/stage/decision/apply/rollback commands; pre-stage decisions are intentionally writes without TOTP, while apply/rollback must claim a fresh operation-bound code.
12. **Rehearse the ordered first start elsewhere:** DB only → bootstrap roles → migrations → fresh training seed/private credentials → app/private readiness and reserved-boundary check → guarded proxy. Verify seed completion and marker, no reserved login, red banner, no outbound calls. Do not use production FIRST_BOOT to simulate staging.
13. **Authorize exposure only after checks:** external no/wrong-Basic tests on pages/API/phone/assets and alternate hosts/ports, valid Basic plus application/TOTP login, forged XFF tests, uploads/offline/relogin, and external IPv4/IPv6 port scans. Verify backups and a reboot. Record the actual app/ops/proxy/DB identities and results without credentials.
