## Rotation and secret handling

For a configured stack, each requested branch is handled as follows (`make-basic.sh:80–101`):

| Branch after hash publication | Result in target source |
| --- | --- |
| `ps -q proxy` fails, with empty or nonempty output | Nonzero, `rotation NOT applied`; stdout content cannot convert a failed command into a successful query (`:86–87`). |
| Query succeeds with no ID | Exit 0, explicitly says a successful query found no running proxy and defers startup to `up.sh` (`:96–97`). No “rotation applied” claim. |
| Query succeeds with ID; recreation fails | Nonzero, old-credential warning (`:91`). Existing service may remain active; the warning is appropriate. |
| Recreation succeeds; health query fails | Nonzero, old-credential warning (`:92–93`), even if the command emitted plausible state before failing. |
| Health query succeeds but is empty, starting, unhealthy, restarting or otherwise not exactly `proxy running healthy` | Nonzero, same warning. Multiple/unexpected rows also fail exact equality. |
| Recreation and exact running/healthy confirmation succeed | Exit 0 and `rotation applied`, followed by an outside-check instruction (`:95`). This is management-plane confirmation; actual new/old credential behavior still needs the documented outside check. |
| Management prerequisite unavailable | Exit 0 without status lookup; incomplete handling in R22-01. |

The first four failure modes in the configured-stack block meet R21's requested nonzero/clear-message rule. A hash generation, validation, chmod or rename failure before publication exits through `set -e` or explicit validation; it does not claim a completed rotation. Not all such early failures emit the new standardized message, and pre-publication failures normally leave the old final file untouched. Signals/host loss are not a durable rotation transaction.

The source has no intentional password/hash output to the operator in the ordinary generated flow. Passwords enter hidden reads or explicitly enabled batch stdin; the password reaches `docker run ... caddy hash-password` on stdin, without a password argument or mount. Bash builtin printf does not create a separate password-bearing executable argv. Generator stderr is suppressed; stdout is captured, shape-checked, and written only to the intended temporary/final hash file. Password variables are unset after successful hashing (`:37–72`). The hash is neither a child environment variable nor a Docker argument. Usernames are validated before being written. The username prompt itself is not hidden, despite the introductory username-and-password claim; this is inherited, and a username is not treated as a secret here.

`umask 077`, `mktemp` and the EXIT removal trap create and initially fill the temporary privately; chmod 0644 immediately precedes the atomic rename (`:18,62–75`). A normal failure cleans up the temporary; SIGKILL, host failure or interruption near publication can leave it behind. The next invocation deletes matching regular files **and links**, including broken links, without following them; directories and nonmatching names are retained. The pattern is anchored to exactly six alphanumeric suffix characters, with a fixed relative parent and quoted removal path. There is no helper-created backup or plaintext-password file.

“Stale” is a naming convention here, not a liveness/ownership determination: no lock, age check or active-writer identity is consulted. Concurrent helper runs are unsupported by these checks; one can remove another's temporary and cause an unsuccessful rotation. Serialize credential changes. An EXIT trap is not a guarantee against uncatchable termination; the INT/TERM handler only restores terminal settings. These are operator/lifecycle limitations, not evidence of remote disclosure.

The universal phrase “never in logs” exceeds what this source-only review can establish. The wrapper's/Compose's stderr remains visible during status and recreation; only recreation stdout is suppressed. A malformed operator-edited Caddy snippet, modified executable, shell tracing, privileged Docker daemon or external binary diagnostic is not constrained by these canary assertions. Caddy access logging remains absent, admin API remains off, and upstream Authorization stripping remains present (`Caddyfile.staging:13–19,82,90–94`). No new normal-flow secret emission was found. The tests' deliberately synthetic curl credentials in argv are test fixtures, not instructions to pass real credentials that way.

## Adversarial `up` argument review

This is a static walk-through of the exact case statement, not execution of Docker or the wrapper. Once **any** token falls outside the five service/flag alternatives, `plain=no` is never reset (`dc.sh:71–79`). Therefore a later safe-looking token cannot cancel the gate.

| Invocation shape after `up` | Gate selection / reason |
| --- | --- |
| Empty; `-d`; `--detach`; `--wait`; combinations/repetition of these flags without a service | Gate: no recognized service name. |
| Exact explicit db/app/ops list, with only `-d`, `--detach`, `--wait` interspersed | Skip: positive allow-list. Repeating or mixing these names does not add proxy. |
| `--wait-timeout 60`; `--wait-timeout=60`; `-t 60` | Gate: option itself is outside the list, irrespective of interpreting its value. Same with explicit db/app/ops appended. |
| `--scale proxy=1` or `--scale=proxy=1` | Gate: unknown option/token. Adding a db token cannot undo it. |
| `--no-deps`; `--force-recreate`; `--build`; `--pull`, with or without values/services | Gate: none is a skipped plain flag. This is conservative even for forms that could only start db. |
| Combined short flags, e.g. `-dw`, or attached short-option values | Gate: only the exact token `-d` is accepted. |
| `--` separator, before or between services, including repeated separators | Gate: separator is outside the allow-list. |
| Proxy alone, mixed with db/app/ops, or repeated | Gate: `proxy` is outside the skip list. |
| Changed case (`DB`, `App`, `PROXY`), unknown service, empty token, whitespace/path-like token | Gate: exact case-sensitive token matching. |
| `up-proxy` with any trailing arguments | Gate unconditionally (`:67`), before its translated Compose invocation. |
| Global options before the subcommand, changed-case subcommand, alternative start/restart/create/watch command | Wrapper refuses the first argument (`:43–46`); none is an additional ungated start subcommand. |

`up app` follows only app → db (`docker-compose.staging.yml:92–94`); it cannot follow the inverse proxy → app dependency. `up db` has no proxy dependency. Explicit `up ops` activates the ops service/profile, which has **no** depends_on edge to proxy (`:144–171`). The wrapper enables all profiles only for effective-config validation (`dc.sh:62`), not as a side effect on the later up command (`:59,117`). Even if ops is explicitly targeted, that does not select default proxy services. `run` can target only ops and its options are separately allow-listed; `exec` runs only in existing containers (`release-lib.sh:93–114`). Pull/config/status/log/stop/down paths do not create a running proxy. No ordinary option-parsing bypass of R21-02 was found.

The 13-form × four-unsafe-fixture matrix checks the original variants before any container-creating up call. It does **not** invoke the actual Compose argument parser: its Docker stub accepts forms such as an unknown option even under the “good gate” control. Those successful controls establish forwarding/gate behavior, not that Docker would accept every invocation. The positive skip controls cover db/app, not explicit ops; the absence of a proxy dependency for ops was checked from source here.

## Directory allow-list and startup paths

For a listable directory, the three quoted-parent glob patterns cover ordinary names, single-dot-prefixed names and double-dot-prefixed names, excluding just `.` and `..`. Matching is against a basename obtained by removing the fixed `staging/` prefix. The documented three names are exact and case-sensitive; the temporary regex is anchored at both ends. Extra extensions, alternate case, whitespace/newlines, Unicode look-alikes and longer/shorter temporary suffixes do not satisfy it. A slash cannot exist inside a filesystem basename, so `../` cannot be smuggled through an entry name. Percent-encoding has no special interpretation here.

After name classification, symlinks (including dangling links and links with approved names) and nonregular files/directories are refused. `staging/` itself cannot be a symlink. The error prints a shell-escaped **name**, not file contents (`dc.sh:89–106`). A secret embedded by an operator in a filename would consequently appear in that diagnostic; do not describe it as a general-purpose name-redaction mechanism. R22-02 is the exception when enumeration fails.

This is not a content allow-list: arbitrary content or a hard link with an approved regular-file name is not distinguished from a genuine helper/documentation file. Nor are all owners/modes of documentation/temp files verified; final-hash owner and permission validation is separate (`:107–113`). A same-UID/deploy or root actor is trusted, and can also change the directory after validation or after startup. Owner-only directory writes, trusted parent directories and serialized administration remain assumptions. New files added after a successful check become visible through the whole-directory mount; no continuous watcher enforces the list. None of these extra names is automatically imported or served: the Caddyfile imports one fixed hash pathname and has no file server.

`up.sh:43` invokes `dc.sh up-proxy`, which selects the check unconditionally. Its earlier db/app starts skip the gate without mounting staging into those services. `rehearse.sh:51–55` calls the actual helper and ordered up script, so its ordinary proxy start reaches the same gate. The helper's rotation names proxy explicitly, uses a non-plain force-recreate flag and therefore reaches the gate too (`make-basic.sh:91`). This establishes the call paths, not an executed rehearsal. Direct Docker commands and daemon auto-restarts are outside wrapper enforcement; this policy is not a permanent host filesystem boundary.
