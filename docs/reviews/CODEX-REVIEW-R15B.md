## Scope C — completed source review (through exact final `f9a4135`)

In this section, shortened `domain/` and `service/` references are under `src/modules/importer/`.

**Transaction and serialization changes verified in source:** apply marks success after an acknowledged COMMIT; rollback checks its final commit too; failed transaction ends destroy the client. A lost transport at COMMIT reports unknown rather than applied. Exceptions attempt cleanup before propagating a nonzero failure. The shared advisory lock precedes the previous-run query and planning, removing the original import/import check/use race. This lock does not serialize screen writers. Server SQLSTATE alone is used to classify a commit error as certainly failed (`tx-end.ts:32-35,50-52`); unusual transaction-resolution errors and process termination still need evidence, rather than a blanket durability assurance.

**Parser and reconciliation:** ordinary double-quoted 1904 metadata is refused; duplicate accepted headers (including optional fields), unclosed CSV quotes and ordinary formula cells are handled as claimed. Formula opt-in is explicit and counted. These controls do not make the regex XML reader a strict workbook gate: alternate attribute quotes can reintroduce exactly the original wrong calendar (R15B-08). Existing payload comparisons improve refusals, but use a blank-as-unspecified, case-folded comparison, not byte equality. Financial party-name lookups select one ID where several can match (R15B-09). Existing opening date wins over the explicitly confirmed option (R15B-11). Positive row counts alone do not reconcile interpreted dates, identities and opening totals.

**Idempotency:** prior run matching is still file-bytes-only (`workbook-import.ts:284-295`). Unmapped sheets remain a warning and may be skipped during a successful apply (`:163-175,233-237`), as documented. For a real-data gate the accepted sheet inventory must be reconciled explicitly; “whole file” means the selected mapped sheets, not every sheet's records.

**TOTP/typed phrase:** the six-digit step is atomically claimed in the same table as web authentication; per-account failures persist across process restarts; eligibility is re-read. The CLI computes the full operation digest over full file hash, mapping array and opening option and checks the exact typed phrase (`scripts/import-excel.ts:200-220`). No 12-hex confirmation remains. The importer recomputes this operation. Proofs have no expiry/nonce/signature and can be reused by a trusted programmatic caller; no untrusted endpoint accepting them was found. This is flow binding and replay protection of the entered TOTP, not a hostile database-client boundary.

**`runImport` extra:** removed from the public barrel (`index.ts:10-17,32-45`), as is the unsafe legacy formatter. Treat this as module-surface hardening only, not an independent REAL_DATA authorization guard. No current untrusted call path was established.

**Reports/audits:** targeted worksheet-name/unit-value leaks are corrected, and private reports plus fixed unexpected-error codes are present. ### High

**R15B-01 — named timing remains reconstructible through the ordinary trip board and the started oracle.**

Verified in source: `src/modules/operations/service/trip-service.ts:74-88,100-121` supplies driver identity, plans, event timestamps and computed durations; permissions `domain/permissions.ts:67,300-308` under platform-security admit partner/support. The ordinary `/[locale]/trips` page checks that permission, calls `listTrips` for the requested date and passes the result to its board (`src/app/[locale]/(protected)/trips/page.tsx:23-27,46`). `0122_trip_tap_read_scope.sql:10-12` preserves partner read, and `0059_trip_tracking.sql:39` preserves support read. `0119_dispatch_serialization.sql:8-15` adds an unscoped definer `trip_started(uuid)`; the dispatch service calls it at `:264` and returns `started`. The ordinary dispatch page serializes that day to its board while reserving the separate timing panel for owner/app_admin/plant_manager (`src/app/[locale]/(protected)/dispatch/page.tsx:47-65`).

Scenario: support or partner reads the normal board for successive days and computes named waiting/unloading/return times or compares taps to plan, despite being denied `trip_delay`. Polling the dispatch `started` flag before any ordinary event additionally bounds the hidden loading-start time. A manager with a known foreign UUID can query the unscoped boolean through the app database login; full foreign raw history is not thereby established. Decision 194 acknowledges support's board but does not eliminate partner's equivalent path. This may be an intentional role entitlement, but it does **not** satisfy a rule that those roles cannot reconstruct driver performance. Require an explicit access-purpose decision and either accept/disclose the timing entitlement or remove/redact all reconstructible sources, including the oracle.

**R15B-08 — the 1904-calendar refusal still fails open on valid alternative XML syntax.**

Verified in source: `src/modules/importer/domain/sheet.ts:134-140` recognizes only an unprefixed `workbookPr` and a double-quoted literal `date1904`; `:258-261` always decodes numeric dates from 1899-12-30. XML attribute values may use either quote character ([W3C XML 1.0, AttValue](https://www.w3.org/TR/xml/#NT-AttValue)).

Scenario: a 1904 workbook carries `<workbookPr date1904='1'/>`, with ordinary double-quoted sheet relationships and cells. The flag is not recognized; a plausible modern cheque/price/recipe serial is accepted about four years early, recreating R14-04. Numeric character references in the flag are another unhandled representation; namespace-prefix variants are not parsed either. No cached-formula opt-in or amount check detects the wrong calendar. Use namespace-aware XML parsing and positive metadata validation, or reject unsupported representations before cell interpretation. A synthetic alternate-quote workbook is required before closure; it was not generated or run here.

**R15B-09 — non-unique exact names can silently attach money to the wrong party.**

Verified in source: `service/importers.ts:689-693,700,794-803,819-824` stores code and normalized name in the same single-value Map; duplicate names overwrite earlier IDs. `:289-290` similarly chooses one existing client for equality testing. `src/modules/master-data/service/client-service.ts:63-67,126-137,165-185` lists by code and permits same-name clients with a warning; database `0018_client.sql:38-58` has no unique-name constraint.

Scenario: two active person clients have exactly the same name and distinct codes. A cheque or opening-balance sheet supplies that name (explicitly allowed by `docs/IMPORT-EXCEL.md:35-36`). Planning selects the later Map entry, all checks pass, and the financial record is committed against that person rather than the intended one. No concurrency or malicious caller is needed. A name that equals another record's code can also collide in the combined namespace. Require explicit code/ID or a unique, positively reconciled name match; refuse every ambiguous lookup, including recipes/components and suppliers where applicable. Counts and a full hash cannot prove identity correctness.

**R15B-11 — the opening date confirmed by the operator can differ silently from the one used.**

Verified in source: `service/importers.ts:791-792` selects `state.openingDate` before `ctx.openingDate`, without mismatch refusal; `:854-856` also accepts ALREADY_ENTERED without re-reading equality. `scripts/import-excel.ts:200-220` binds/prompts the operator for the supplied option. `src/modules/ledger/service/opening-service.ts:63-67` inserts balances against the database's singleton opening state.

Scenario: the database is already opened on E. The operator imports a new party balance with `--opening-date F`, reads a clean report, confirms the digest covering F and gives TOTP. Apply writes the balance into books opened on E, with no conflict or explicit actual-date reconciliation. A screen setting another date during planning creates a related race. The documented rule that a second file cannot *move* the singleton is sound; silently ignoring a contradictory positive instruction is unsafe admission. Refuse a supplied mismatch and verify the actual date under the write's locking discipline; bind/show the effective date and reconcile it with the accountant.

### Medium

**R15B-02 — failed logout is treated as finished, and reload can restore the session.**

Verified in source: `field-session.ts:227-251` under `src/modules/field/ui/` suppresses transport errors and never checks `Response.ok`; timeout abort resolves the login barrier. Server `src/app/api/field/logout/route.ts:7-13` only deletes the cookie; it does not revoke the server session/device. `field-app.tsx:272-280` starts a session read on mount.

Scenario: A signs out while offline or the logout receives a failed response. The screen clears and the transport is eventually considered settled, but the cookie remains valid. On reload with connectivity A's day returns without a new PIN. This same-driver restoration is acknowledged in decision 187; it is not a demonstrated A-to-B data disclosure. Across two pages the per-page logout barrier also cannot order competing cookie-setting/deleting responses. Require a confirmed revocation/deletion state or a persistent local sign-out tombstone before claiming logout survives reload; real-browser cookie evidence is still missing. The original stuck-global-flag bug is corrected.

**R15B-04 — photo puts/deletes report success before their IndexedDB transaction commits.**

Verified in source: `photo-queue.ts:40-46,58-65,99` resolves from `IDBRequest.onsuccess`, with no transaction complete/abort handling for put/delete. `wipePhotos` correctly uses transaction completion (`:94-96`). A request can succeed before its enclosing transaction later fails; this is explicitly distinguished in the [IndexedDB transaction API](https://www.w3.org/TR/IndexedDB/#dom-idbtransaction-oncomplete).

Scenario: a capture's put succeeds, then its transaction aborts during commit (storage write failure). The caller can receive “kept”/“queued” while no photo survives. Conversely, a stale photo's compensating delete may report success before abort and leave the pre-logout row present; errors are also suppressed at `:64`. Session guards prevent the original owner swap, but do not certify storage or erasure. Resolve writes/deletes on transaction completion, reject transaction aborts, and expose cleanup failures without allowing handover to rely on a false erasure assurance.

**R15B-05 — reassignment can introduce an unrelated driver's overlap without an audited exception.**

Verified in source: `dispatch-service.ts:513-535` rebuilds all movable rotations; `:407-416` retimes them but filters overlap enforcement to the selected draft key. `domain/dispatch.ts:208-224` closes gaps independently per truck; `:267-275` reports any driver overlap. Both paths are under the day lock; the defect is what is judged, not missing locking.

Scenario: truck T1 has A's first rotation then B's next rotation; T2 has B's first rotation. Initially B's T1 work follows B's T2 work, so no B overlap exists.
